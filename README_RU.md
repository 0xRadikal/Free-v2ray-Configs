# ⚡ Ссылки подписки

> **Не уверены, что выбрать?** Берите `verified` — каждая запись в нём ответила на
> реальный HTTP-запрос через прокси во **всех трёх** независимых раундах теста:
>
> ```

>
> Нужен максимально большой список, а не самый надёжный? Замените `verified` на `all`.

## 🎛️ Выберите категорию (tier)

Каждый запуск публикует шесть категорий. Это не разные источники — это **один и тот же
пул, отфильтрованный по тому, сколько есть доказательств, что конфиг действительно
работает**.

**Какой формат?** `configs_base64.txt` — классический формат подписки и самый безопасный
выбор по умолчанию. `configs.txt` — тот же список без кодирования. `clash.yaml` — готовый
профиль mihomo/Clash; `singbox.json` — готовый конфиг sing-box. Оба перед публикацией
проверяются реальными бинарниками (см.
[ниже](#-every-release-is-checked-by-the-real-clients)).

## 🪞 Зеркало (jsDelivr) — только если `raw.githubusercontent.com` заблокирован

Замените префикс `https://raw.githubusercontent.com/0xRadikal/Free-v2ray-Configs/main`
на `https://cdn.jsdelivr.net/gh/0xRadikal/Free-v2ray-Configs@main` — каждый путь выше
существует на зеркале без изменений.

```
https://cdn.jsdelivr.net/gh/0xRadikal/Free-v2ray-Configs@main/verified/configs_base64.txt
```

**Предпочитайте raw, когда можете.** Это собственная `link_policy` репозитория, а не
мнение:

| | директива кэша | худшее устаревание |
|:--|:--|:--|
| `raw.githubusercontent.com` | `max-age=300` | **5 минут** |
| `cdn.jsdelivr.net` (ссылка на ветку) | `s-maxage=43200` | **12 часов** — в 144 раза дольше |

Кэш CDN сбрасывается при каждом запуске, но сброс очищает только край сети; сам origin
jsDelivr может отставать, пока заново разрешает имя ветки. Если нужна гарантированно
точная копия через CDN, закрепите коммит вместо ветки: `@<commit-sha>/…`.

> 📌 **Всё лежит в ветке по умолчанию (`main`).** Никаких переключений веток, ничего не
> спрятано — ссылка, скопированная месяцы назад, продолжает работать. Почему это не так
> очевидно, как звучит:
> [почему публикация остаётся дешёвой](#-how-publishing-stays-cheap-and-why-the-files-live-on-main).

# 🧪 А оно вообще работает?

Большинство репозиториев с бесплатными конфигами публикуют большое число и предлагают
вам догадываться. Вот неудобный ответ, **измеренный, а не прикинутый**: в любой момент
подавляющее большинство любого пула бесплатных конфигов мертво. Это свойство бесплатных
конфигов, а не этого репозитория — поэтому вместо того, чтобы это скрывать, каждый запуск
это измеряет и сортирует по результату.

Каждый конфиг проходит четыре стадии. Каждая достаточно дешёвая, чтобы прогнать её по
всему пулу, и каждая отбрасывает работу, которую следующая потратила бы впустую:

<div align="center">

<img alt="The four-stage pipeline: collect, repair, dial, prove, publish" src="https://raw.githubusercontent.com/0xRadikal/Free-v2ray-Configs/main/assets/pipeline.svg">

</div>

| Стадия | Какой вопрос задаёт | Чего стоит |
|:--|:--|:--|
| **L0 / L1** | Парсится ли? Уникален ли endpoint, маршрутизируем ли он? | без сети |
| **L2** | Принимает ли TCP-порт соединение на самом деле? | одно подключение на уникальный endpoint |
| **L3** | Проходит ли **реальный HTTP-запрос через прокси**? | полный handshake, повторённый **3×** |
| **buckets** | Какие прошли *каждый* раунд L3? | только сортировка |

Конфиг попадает в `verified/` только если прошёл **каждый** раунд — никогда не по своему
лучшему.

<a name="-every-release-is-checked-by-the-real-clients"></a>

# ✅ Каждый релиз проверяется реальными клиентами

**Одна** некорректная запись заставляет клиент отвергнуть **весь файл** — поэтому вывод
«в основном валидный» не стоит ничего. Перед публикацией каждый сгенерированный
`clash.yaml` и `singbox.json` разбирается теми же бинарниками, которые запускаете вы:

```bash
sing-box check -c <file>      # sing-box 1.13.14
mihomo -t -f <file>           # mihomo   v1.19.29
```

Оба бинарника при загрузке в workflow **закреплены по версии и проверены по SHA256**.
Если хоть один файл не проходит проверку, **запуск прерывается и ничего не коммитится** —
предыдущий рабочий релиз остаётся ровно на месте.

> ⚠️ **Структурная валидность — это не то же самое, что работоспособность.** Структурно
> битые записи (нулевой UUID, `App not supported`, неподдерживаемые шифры, некорректные
> ключи REALITY) отбрасываются, но синтаксически безупречный конфиг всё равно может быть
> мёртвым. Это отдельный вопрос, и отвечает на него отдельно
> [каскад L3 выше](#-does-it-actually-work).

## 🏷️ Стабильные имена, производные от содержимого

Каждый remark переписывается в `{CC} {flag} | @Raydikalx | {id}`, где `{id}` —
`sha256(dedup-key)[:6]`, то есть **производная от самого конфига, а не от его позиции в
списке**. Поэтому один и тот же сервер всегда получает одну и ту же метку, и имена
записей в вашем клиенте остаются стабильными между обновлениями, а не перетасовываются
каждые 15 минут.

Написанное человеком, с нормальной историей git и blame:

```
scripts/    конвейер — core · sources · filters · converters · geo · reachability
            realtest · pipeline · aggregate · validate · state (+ test_pipeline.py)
.github/    workflow по расписанию · конфиг Dependabot · шаблоны issue
docs/       живая панель состояния (читает index.json / health.json в браузере)

SECURITY.md · CONTRIBUTING.md · LICENSE
```

Два правила, которые легко упустить и которые важны:

- **Пустые файлы никогда не публикуются.** Файл в `protocols/` или `archive/` появляется
  только тогда, когда в нём есть содержимое. Пустой файл был бы *хуже* 404: подписанный
  на него клиент заменил бы свой рабочий список пустотой, тогда как при 404 клиенты
  сохраняют то, что у них уже есть.
- **`index.json` объявляет ровно те файлы, которые существуют** — его список URL никогда
  не является обещанием, которое репозиторий не может выполнить.

<a name="-how-publishing-stays-cheap-and-why-the-files-live-on-main"></a>

# 🌿 Почему публикация остаётся дешёвой (и почему файлы лежат в `main`)

Git никогда не забывает blob. Каждый запуск по расписанию заново генерирует один и тот же
набор больших файлов, и добавление их в ветку обычным способом навсегда добавляет в
историю **новую постоянную копию** каждого изменённого файла. Тогда публикация стоит
**O(числа запусков)**, без верхней границы. При ~96 запусках в сутки это не теоретическая
проблема: история этого репозитория успела дорасти до **≈ 3,6 ГиБ** до исправления.

### ❌ Неправильное решение (попробовали и откатили)

Перенести вывод в **orphan-ветку** и force-push'ить одним коммитом. Стоимость публикации
действительно упала до O(1) — и проект тихо сломался:

- **Каждая ранее скопированная ссылка подписки стала возвращать HTTP 404.** Пользователь,
  чей клиент указывал на `…/main/all/configs.txt`, не получал диалога с ошибкой —
  подписка просто молча становилась пустой.
- **Посетитель, открывший репозиторий, вообще не видел конфигов** — только код.
  Большинство людей, ищущих конфиг, не знают, что такое ветка git, и уж тем более не
  догадаются переключиться на вторую и посмотреть снова.
- **Обнаруживаемость обрушилась.** Поиск GitHub, главная страница и поисковые системы
  индексируют ветку по умолчанию.
- **Ни один успешный репозиторий в этой нише так не делает.** Проверено напрямую:
  `Epodonios/v2ray-configs`, `mahdibland/V2RayAggregator`, `Pawdroid/Free-servers` — все
  публикуют в своей ветке по умолчанию.

Дешёвая история не стоит ничего, если файлы никто не может найти.

### ✅ Правильное решение — rolling squash в `main`

Вывод публикуется **в ветку по умолчанию**, но сама ветка удерживается в состоянии
*история исходников + ровно один коммит с выводом*:

1. Найти самый свежий коммит, **не** помеченный `[auto-output]` — **anchor**.
2. Построить дерево = *дерево anchor'а* + *свежий вывод этого запуска*.
3. `git commit-tree <tree> -p <anchor>` и push **с lease**.

Предыдущий коммит с выводом становится недостижимым и удаляется сборщиком мусора. Это
видно прямо в логе — он строго чередуется, один коммит с выводом на каждый человеческий
коммит, сколько бы запусков ни прошло между ними:

```
94a939f23  bot     chore: update configs — 07:42 UTC — 10116 configs   ← единственный живой вывод
e5a0e7dbf  human   docs: rebuild the status dashboard …
a72b66717  bot     chore: update configs — 22:12 UTC — 10146 configs
19b8d6cca  human   docs(security): document the branch and tag rulesets …
```

Стоимость публикации — **O(1)**, при этом каждый файл остаётся ровно там, где его уже
ищут пользователи и краулеры.

Каждое свойство безопасности ниже подтверждено исполняемым тестом:

- **`--force-with-lease`, никогда просто `--force`.** Публикация идёт в ту же ветку, куда
  коммитят люди, поэтому наивный force-push удалил бы их работу. Запущено как
  отрицательный контроль: с обычным `--force` число коммитов владельца на удалённом
  репозитории упало до **0**. С lease действительно конкурирующий push отвергается, шаг
  заново берёт anchor, и коммит владельца, и новый вывод остаются целы.
- **Защита от регрессии исходников.** Каждый путь, различающийся между anchor'ом и
  вершиной, классифицируется; если изменилось что-либо вне набора выходных путей, шаг
  отказывается публиковать, вместо того чтобы откатить чей-то код.
- **Учёт shallow-checkout.** `actions/checkout` тянет глубину 1, поэтому обычно
  единственный видимый коммит — это коммит с выводом, и поиск anchor'а ничего не нашёл бы,
  что навсегда остановило бы публикацию. Шаг постепенно углубляется (2 → 4 → 8 → 32),
  пока anchor не появится. (`fetch-depth: 0` отвергнут: клонировать гигабайты 96 раз в
  день.)
- **Fail-closed везде.** Отсутствующий вывод, подозрительно маленький файл конфигов или
  пустое дерево прерывают публикацию и оставляют предыдущий рабочий релиз на месте.
- **Без рекурсии.** Push'и, сделанные с `GITHUB_TOKEN`, не запускают новые workflow, а
  триггер `push` дополнительно ограничен путём `scripts/**`, куда бот никогда не пишет.

### 🧊 Вывод детерминирован намеренно

Rolling squash ограничивает историю; детерминизм делает diff каждого раунда
действительно маленьким. Измерениями были найдены и устранены три источника
бессмысленного «шума»:

| Было | Стало |
|:--|:--|
| Метка страны бралась у того источника, который скачался первым — один и тот же сервер прыгал `RU 🇷🇺` ⇄ `US 🇺🇸` между запусками | Метка привязана к **endpoint'у**; первое решающее определение побеждает и фиксируется |
| Метка в remark была **позиционным счётчиком** — вставка одного конфига переименовывала все строки после него | Метка — `sha256(dedup-key)[:6]`, производная от содержимого и не зависящая от позиции |
| Порядок строк следовал порядку сетевых ответов | Сортировка по ключу дедупликации — один и тот же набор конфигов даёт один и тот же файл, побайтово |

Детерминизм **не** означает, что файлы перестают меняться; он означает, что они меняются
*только тогда, когда меняются данные* — а «шум», который раньше возникал *без* изменения
данных, исчез.

### 🩹 Одна честная оговорка

Уже накопленные в истории ≈ 3,6 ГиБ **не** были переписаны. Поскольку GitHub разделяет
объекты внутри сети форков, перезапись почти ничего не освободила бы, но сломала бы все
существующие клоны и оба форка. Кровотечение остановлено на будущее; старый шрам оставлен
намеренно.

Пересоздаётся при каждом запуске. Для каждого из 21 источника записываются `status`

# ⚙️ Как это работает

1. **Загрузка** — 21 источник скачивается параллельно, с автоопределением base64/простого
   текста. Повторы при временных ошибках, но быстрый отказ на 4xx, чтобы мёртвый URL был
   *отражён в отчёте*, а не молча опрашивался вечно.
2. **Очистка** — отбрасываются пустышки и структурно битые записи (нулевой UUID,
   `App not supported`, пустые proxies, немаршрутизируемые серверы).
3. **Дедупликация** — отпечаток идентичности сервера с учётом CDN, поэтому хост за
   меняющимися IP CDN сводится к одной записи, а не появляется десятки раз.
4. **Брендинг** — каждый remark переписывается в `{CC} {flag} | @Raydikalx | {id}` с
   `{id}`, производным от содержимого, и меткой страны, привязанной к endpoint'у.
5. **Конвертация** — трансляция схемы под каждый клиент со строгой проверкой полей: белые
   списки шифров, длины ключей SS-2022, uTLS для REALITY, проверка формата
   `short-id` / публичного ключа и полная передача транспорта (`ws` / `grpc` / `h2` /
   `http` / `httpupgrade` / `xhttp`). Записи, которые клиент не может выразить,
   **отбрасываются, а не понижаются молча** — понижённый конфиг выглядит валидным и
   никогда не подключается.
6. **Проверка** — `sing-box check` + `mihomo -t` для каждого сгенерированного файла.
   **Любая ошибка прерывает запуск.**
7. **Тест** — каскад L0→L3 реально подключается через прокси, три раза, и строит
   `verified/`, `fast/`, `secure/` и `top100.txt`.
8. **Публикация** — коммит rolling-squash в `main` плюс сброс кэша jsDelivr.

## ⏱️ Надёжное расписание ~15 минут

Cron в `schedule:` у GitHub работает «по возможности» и в загруженные периоды часто
задерживается или пропускается. Чтобы всё равно держать стабильный ритм, этот репозиторий
использует **три слоя**:

1. **Частый cron** (`*/5 * * * *`) — больше шансов, что запуск реально произойдёт.
2. **Проверка свежести** — каждый тик завершается досрочно, если `index.json` обновлялся
   менее 13 минут назад, поэтому тяжёлая работа выполняется примерно раз в 15 минут: без
   лишних запусков и без двойных обновлений.
3. **Резерв через `repository_dispatch`** — постоянно работающий бот каждые 15 минут
   отправляет событие `aggregate-now`, гарантируя запуск, даже если cron был пропущен
   полностью. Ручной `workflow_dispatch` (с необязательным `force`) тоже поддерживается.
